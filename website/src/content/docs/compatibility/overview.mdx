FrogDB implements RESP2 and RESP3 and targets compatibility with the Redis {versions.redis_compat_target} command set. Standard Redis client libraries connect without modification. This page documents only the behavioral differences; for standard Redis behavior, see the [Redis documentation](https://redis.io/docs/). For the exact per-command support status, see the [Command matrix](/compatibility/command-matrix/); for the regression evidence behind the compatibility claim, see [Test suite results](/compatibility/test-suite/) and [Testing methodology](/compatibility/testing-methodology/).

FrogDB advertises `redis_version:{versions.advertised_redis_version}` in `INFO` and to the Lua `REDIS_VERSION` binding, so client libraries that feature-detect on the reported version behave as they would against that Redis release. The compatibility *target* — the command set and regression suite FrogDB is measured against — is Redis {versions.redis_compat_target}.

## Architecture

| | Redis | FrogDB |
|---|---|---|
| Command processing | Single-threaded (separate I/O threads for socket reads/writes) | Shared-nothing, sharded worker threads |
| Storage engine | In-memory with RDB/AOF files | In-memory with a RocksDB write-ahead log and SST files |
| Cluster coordination | Gossip protocol | Raft consensus with an orchestrated control plane |
| Configuration format | `redis.conf` | `frogdb.toml` (TOML) |
| Allocator | jemalloc | jemalloc |
| Lua version | 5.1 | 5.4 |

## Persistence

FrogDB persists data through RocksDB rather than Redis RDB snapshots and AOF logs:

- **No RDB or AOF files.** Data lives in RocksDB SST files fronted by a write-ahead log.
- **`CONFIG GET appendonly` returns `no`.** There is no AOF behind it to report on, so this is a truthful answer rather than a fabricated one; `CONFIG SET appendonly` is accepted and ignored. Use `persistence.enabled` (see [Configuration](#configuration) below) to control FrogDB's own durability.
- **Forkless `BGSAVE`.** `BGSAVE` triggers a snapshot without a `fork()` of the server process.
- **No `BGREWRITEAOF`.** RocksDB manages WAL rotation and compaction internally.
- **Durability modes** are `async`, `periodic`, and `sync` (`persistence.durability-mode`), replacing Redis `appendfsync always/everysec/no`. In `sync` mode the server waits for an fsync before acknowledging a write.
- **Redis RDB files cannot be imported.** The on-disk formats are unrelated.

See [Persistence & durability](/operations/persistence/) for configuration and recovery details.

## Configuration

FrogDB is configured with a TOML file instead of `redis.conf`. Common mappings:

| redis.conf | frogdb.toml |
|---|---|
| `bind 0.0.0.0` | `server.bind = "0.0.0.0"` |
| `port 6379` | `server.port = 6379` |
| `requirepass secret` | `security.requirepass = "secret"` |
| `maxmemory 1gb` | `memory.maxmemory = "1gb"` |
| `maxclients 10000` | `server.max-clients = 10000` |
| `appendonly yes` | `persistence.enabled = true` |
| `appendfsync everysec` | `persistence.durability-mode = "periodic"` |
| `save 900 1` | `snapshot.snapshot-interval-secs = 900` |

Environment variables use the `FROGDB_` prefix with double underscores for nesting, e.g. `FROGDB_SERVER__PORT=6380`. Runtime changes made with `CONFIG SET` can be written back to the TOML file with `CONFIG REWRITE`, which merges the current runtime values into the existing document and preserves its comments.

See [Configuration](/operations/configuration/) for the four configuration surfaces and precedence, and the [Configuration reference](/reference/configuration/) for every parameter.

## Clustering

FrogDB coordinates cluster membership with Raft consensus rather than Redis Cluster's gossip protocol:

- **Orchestrated control plane.** There is no `CLUSTER MEET`; topology is managed through the admin API.
- **Deterministic failover.** Raft leader election replaces gossip-based failover.
- **Two-level sharding.** The 16384 cluster hash slots are mapped onto internal shard workers.
- `CLUSTER BUMPEPOCH` is not supported.
- Replica migration is manual rather than automatic.

See [Clustering](/operations/clustering/) for bootstrap steps, the admin API, and failure modes.

### A quorum-fenced node refuses reads too

When a cluster node cannot reach a quorum of its peers, `cluster-self-fence-on-quorum-loss` (on by default) fences it. Writes are refused — that part is unsurprising — and so are reads:

```
CLUSTERDOWN The cluster is down (quorum lost, stale reads refused)
```

A node that cannot reach the quorum cannot learn it has been failed over and its slots reassigned, so its keyspace is a snapshot of unbounded age. Refusing only writes would leave the half of the split-brain hazard that produces no error anywhere.

Redis's equivalent is `cluster-allow-reads-when-down`, which also defaults to refusing. FrogDB has **no second knob**: the opt-out is `replica-serve-stale-data`, the same setting that reopens a link-down replica, because both cases mean the same thing to a client. Setting it to `yes` reopens reads on a fenced node; it never reopens writes. `stale`-flagged commands (`PING`, `INFO`, `CONFIG`, `COMMAND`, `AUTH`, …) are answered either way, so a fenced node stays diagnosable.

**No staleness bound is offered.** There is no max-age argument, no read timestamp, and no follower-read lease. A partitioned FrogDB node is either unavailable or unbounded — never "at most N seconds behind". Redis offers no bound here either.

## Replication

### Stale reads are refused by default

`replica-serve-stale-data` defaults to **`no`** in FrogDB and `yes` in Redis. This is the one replication default FrogDB deliberately inverts.

While a replica's link to its primary is down — broken, or not yet streaming — a FrogDB replica refuses every command that is not `stale`-flagged with Redis's own error:

```
MASTERDOWN Link with MASTER is down and replica-serve-stale-data is set to 'no'.
```

`INFO`, `PING`, `CONFIG`, `AUTH`, `REPLICAOF`, `SHUTDOWN` and the rest of the `stale`-flagged set keep working, so the node stays diagnosable and re-pointable while the gate is closed. `COMMAND INFO` reports the flag, so a client can tell in advance which commands survive.

The reasoning: a link can stay down indefinitely, and Redis's default answers those reads silently — no bound on their age, no signal a client can act on. FrogDB fails fast instead, the way CockroachDB and FoundationDB do, and leaves unbounded staleness as something an operator asks for by name. Everything else about the knob is Redis-compatible.

To get Redis's behaviour back, at boot or live mid-incident:

```
CONFIG SET replica-serve-stale-data yes
```

This gate is replica-only — a primary or standalone node has no link to lose — and never applies to the replication stream itself. The same knob also governs the cluster-side fence below, which is not replica-only.

## Cross-slot & multi-shard operations

FrogDB partitions keys across internal shards even in standalone mode, so multi-key operations are subject to slot rules that plain single-node Redis does not enforce.

In **cluster mode**, multi-key commands (`MGET`, `MSET`, and similar) require all keys to hash to the same slot, or they return `-CROSSSLOT`. In **standalone mode**, cross-slot multi-key operations also return `-CROSSSLOT` by default. Set `server.allow-cross-slot-standalone = true` to allow them via scatter-gather; note that `MSETNX` always requires same-slot keys.

### Transactions

- `MULTI`/`EXEC` requires all keys in the same hash slot in cluster mode.
- In cluster mode, `EXEC` re-validates slot ownership for the whole queued batch and can therefore reply with a bare `-MOVED`, `-ASK`, `-TRYAGAIN`, or `-CROSSSLOT` instead of an array, discarding the queue — as Redis does. A command rejected while *queuing* instead makes `EXEC` reply `-EXECABORT`. See [MULTI/EXEC: validated twice](/architecture/clustering/#multiexec-validated-twice).
- In standalone mode, cross-shard transactions obtain atomicity through [VLL](/architecture/vll/).
- `WATCH` uses per-key version tracking.
- A transaction's memory is bounded by `memory.txn-buffer-limit` (per core, default 512 MiB; floor 1 MiB; adjustable with `CONFIG SET txn-buffer-limit`). A command that would take the queued `MULTI` past it replies `-OOM transaction buffer limit exceeded` instead of `+QUEUED`, and `EXEC` then replies `-EXECABORT`; a batch the shard cannot hold before its first write replies the same `-OOM` from `EXEC` with nothing applied. Redis has no such limit (`proto-max-bulk-len` caps one argument, not the queue), so one client can grow a `MULTI` until the process runs out of memory; the cap trips before anything is applied, so atomicity is unaffected. The effective node-wide bound is the limit times the number of shards. See [FM-TXN-054](/specifications/txn/#fm-txn-054--a-multi-that-outgrows-the-transaction-buffer-is-poisoned-at-queue-time).

### Blocking commands

- Blocking list and stream commands (`BLPOP`, `BRPOP`, `BLMOVE`, and similar) require their keys on the same shard.
- A cross-shard blocking call returns `-CROSSSLOT`. This holds even in standalone mode with `server.allow-cross-slot-standalone = true`: the escape hatch does not extend to blocking commands, because a blocking wait must be registered on a single shard that owns all the watched keys.

## Lua scripting

FrogDB runs scripts on an embedded Lua 5.4 interpreter (Redis uses Lua 5.1), which introduces a few edge-case syntax and semantic differences at the language level. The FrogDB-specific behavioral differences are:

### Undeclared key access

FrogDB does not require a script to declare every key it touches through `KEYS[]`. A `redis.call` against a key that was never declared succeeds, matching Redis, which permits undeclared key access but documents it as unsupported.

```lua
-- Works in both Redis and FrogDB, even though 'mykey' is never declared
EVAL "return redis.call('GET', 'mykey')" 0
```

The one key-safety check a script is subject to is slot cohesion, and it applies only to `#!lua`-shebang scripts running in cluster mode: every key the script touches — declared or undeclared — must hash to the same slot as the first key seen, or the call fails with `Script attempted to access keys that do not hash to the same slot` (Redis's own cluster-mode scripting error). Add `allow-cross-slot-keys` to the shebang's `flags=` list to opt out, matching Redis's `SCRIPT_ALLOW_CROSS_SLOT`. Standalone mode has no such check: a script may touch any key on any shard.

This is a separate concern from the [single-shard requirement](#single-shard-requirement) below, which governs the keys a script *declares* through `numkeys`, not the keys `redis.call` touches while it runs.

### Single-shard requirement

By default, all keys accessed by a script must hash to the same shard; a script spanning multiple shards returns a `CROSSSLOT` error. As with multi-key commands, setting `server.allow-cross-slot-standalone = true` permits cross-shard scripts.

### Other differences

- `redis.setresp()` is not supported and returns an error.

## Pub/Sub

In standalone mode, `PUBLISH`/`SUBSCRIBE` and pattern subscriptions (`PSUBSCRIBE`) behave identically to Redis.

In cluster mode:

- **Regular Pub/Sub** messages are forwarded across cluster nodes, so a subscriber on any node receives them — matching Redis behavior.
- **Sharded Pub/Sub** (`SSUBSCRIBE`/`SPUBLISH`) routes messages to the shard that owns the channel's hash slot, consistent with Redis Cluster.

Unlike Redis, FrogDB enforces a per-client subscription cap, configurable via `blocking.max-subscriptions-per-client` (Redis has no built-in per-client limit).

## Database model

FrogDB exposes a single logical database (`db0`). `SELECT 0` is a no-op; `SELECT` with a non-zero index returns an error. `MOVE` and `SWAPDB` are not supported.

## Not supported

The following commands and features are intentionally absent because they do not fit FrogDB's architecture. The [Command matrix](/compatibility/command-matrix/) is the exhaustive per-command view.

| Command / feature | Reason |
|---|---|
| `SELECT` (non-zero index) | Single-database model |
| `MOVE`, `SWAPDB` | Single-database model |
| `MODULE *` | No loadable-module architecture |
| `BGREWRITEAOF` | No AOF; RocksDB manages WAL lifecycle |
| `SYNC` | Legacy full-sync; superseded by `PSYNC` |
| `CLUSTER BUMPEPOCH` | Raft manages epochs, not manual bumping |
| `DEBUG SEGFAULT` / `RELOAD` / `CRASH-AND-RECOVER` | Unsafe debug subcommands are disabled |
| `redis.setresp()` in Lua | Not implemented |
| ACL selectors v2 (`(...)`, `clearselectors`) | Not supported; use separate users instead |
| Diskless replication | Not applicable; FrogDB does not replicate via RDB transfer |

## Eviction

`maxmemory` and `maxmemory-policy` take Redis's names and mean what they mean in Redis: the policy fixes the *candidate set* (`allkeys-*` may take any key, `volatile-*` only keys carrying a TTL, `noeviction` refuses the write) and the shard evicts only when it is over its limit. What differs is how the coldest key inside that set is found.

| Policy | Redis | FrogDB (default keyspace) | FrogDB (segmented keyspace) |
|---|---|---|---|
| `allkeys-lru`, `volatile-lru` | Sample `maxmemory-samples` keys, evict the one with the oldest 24-bit per-key clock | Same sampled approximation | 2Q over 16 KiB segments; the victim comes from the coldest segment |
| `allkeys-lfu`, `volatile-lfu` | Sample, evict the lowest 8-bit log counter (decayed by `lfu-decay-time`) | Same | Same 2Q ordering — a segment's hit and miss counters stand in for the per-key counter |
| `allkeys-random`, `volatile-random` | Random key from the candidate set | Same | Same (a cold ordering is exactly what `*-random` promises not to use) |
| `volatile-ttl` | Sample, evict the shortest remaining TTL | Same | Same (TTL is a property of the key, not of how recently it was used) |
| `tiered-lru`, `tiered-lfu` | No equivalent | Spill instead of delete — see below | Same, victim chosen by 2Q |

Neither backend implements true LRU or LFU, and neither does Redis: all three are approximations, and FrogDB's differ in *which* approximation. The sampled path is Redis's own algorithm, including the cross-sample eviction pool. The segmented path — selected at build time, not at runtime — ranks whole segments instead of keys, which is how it avoids a per-key recency field altogether; the trade is coarser ordering. Both confine themselves to the policy's candidate set per *key*: a segment holding both TTL'd and persistent keys yields only its TTL'd keys under `volatile-lru`.

This is the same trade Dragonfly makes for the same reason. Dragonfly's segmented hash table evicts from the bucket a new key hashes into rather than maintaining a global LRU, on the grounds that a per-key timestamp is unaffordable at its densities; FrogDB keeps the queue state in a segment header for the same 0-bytes-per-key result, but orders segments globally rather than evicting locally at the insertion point. Every policy remains observable identically to Redis: an eviction fires the `evicted` keyspace notification and is counted by `frogdb_eviction_keys_total` and `frogdb_eviction_bytes_total`.

## Tiered storage

FrogDB offers a two-tier hot/warm store as an alternative to eviction. With the `tiered-lru` or `tiered-lfu` eviction policy, instead of deleting a key under memory pressure FrogDB serializes its value to the RocksDB warm tier (a *spill*); the key's metadata stays in memory and reads transparently deserialize the value back (an *unspill*).

Tiered storage requires persistence to be enabled. Open-source Redis has no equivalent — it only evicts (deletes) keys when memory is full. See the [Configuration reference](/reference/configuration/) for the tiered-storage settings.
